# Four versus 32 Monty sessions

## Follow-up: supported configuration and structured contexts

After implementing `PYDANTIC_AI_RLM_MAX_SESSIONS`, the benchmark now passes the
setting to fresh subprocesses instead of replacing a private semaphore. It now
uses dictionary contexts with tenant and payload fields, exercising the fixed
structured-context traversal as well as concurrency. The original measurements
below describe the earlier text-context version of the benchmark.

The follow-up 32-slot run completed all 32 jobs in 2.719 seconds, observed 32
simultaneous sessions and workers, and passed isolation/state checks. Sampled
worker peak RSS was 337,072,128 bytes; combined Python/worker peak RSS was
493,170,688 bytes. No child processes remained. Verification also passed 98
unit/integration tests, Ruff and mypy for all ten package modules.

```powershell
$env:PYDANTIC_AI_RLM_MAX_SESSIONS = "32"
.venv\Scripts\python.exe benchmarks/compare_parallel_capacity.py --child 32
```

## Original comparison

Measured 2026-09-18, Windows, Python 3.14.3, package source based on b9176ca.
Run ` .venv\Scripts\python.exe benchmarks/compare_parallel_capacity.py` from
the repository root. Raw results are saved to
`benchmark-results/parallel-capacity.json` (ignored by Git).

Each trial starts a fresh Python process and replaces `_SANDBOX_GATE` before
any worker starts, only in that test process. Package defaults are unchanged.
Three trials per capacity, alternating order: 4/32, 32/4, 4/32.
Each trial runs 32 concurrent agent requests on one shared agent, with unique
tenant markers, 1 MiB text context per request, two real Monty code calls,
and a two-second deterministic model wait between calls. No external LLM calls.

| Metric | Four slots | 32 slots |
| --- | --- | --- |
| Batch duration, seconds, three trials | 16.985 / 16.882 / 16.947 | 2.593 / 2.557 / 2.512 |
| Median batch duration | 16.947 s | 2.557 s |
| Observed simultaneous workers in each trial | 4 | 32 |
| Maximum sampled sum of worker RSS | 42.07 MB | 336.06 MB |
| Maximum sampled host plus worker RSS | 166.97 MB | 491.84 MB |
| Parent final RSS after GC | 85.25–87.02 MB | 87.04–88.47 MB |
| Successful requests across three trials | 96/96 | 96/96 |
| Remaining child processes in each trial | 0 | 0 |

MB means decimal megabytes (1,000,000 bytes). RSS is sampled every 50 ms by a
separate host thread; short peaks may be missed and summed RSS may include shared
pages. Combined peaks include the Python host. Worker peak at 32 slots is about
10.5 MB per worker for this workload. Median batch improvement is approximately
6.63x, or 84.9% shorter duration. These timings exclude interpreter startup;
fresh-process wall times are included in the JSON.

All runs passed tenant-marker separation and within-session state checks. This
demonstrates 32 simultaneous real sessions in a single host process for an
I/O-wait-oriented workload. It does not measure CPU-intensive scaling, external
provider rate limits, arbitrarily large contexts, or long-duration memory growth.
The 30-second checkout timeout used by the fixture is identical in both arms.

Conclusion: four slots are not a Monty technical ceiling. A configurable
process-wide capacity of 32 is plausible for this workload; resource budgets
must account for contexts, generated allocations, host memory and all app
processes. The configured 256 MiB sandbox memory allowance is per session,
not the observed 10.5 MB footprint. At 32 slots the sum of these allowances is
8 GiB, before host overhead. Production still defaults to four slots.
